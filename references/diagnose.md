# 排查漏同步

只读排查，从具体来源 ID 开始。不要先重放事件、删除映射、把状态批量改待同步，或临时放宽筛选。

## 先确认是哪一种对象

- URL 路径 `issue/detail`：缺陷规则与缺陷入表流程。
- 需求详情节点下的任务：子任务 ID，与父需求 ID 区分。
- 飞书独立待办 Task：不属于本包的节点子任务模板。

读取标题、空间、类型、经办人/负责人、报告人、创建时间与操作历史。截图出现自己的头像，只能证明对应字段的身份，不能证明经办人正确。

## 按证据追到阻断点

| 检查层 | 具体证据 | 常见判断 |
|---|---|---|
| 飞书项目规则 | 是否启用、事件种类、过滤角色、目标地址 | 经办人为空、报告人匹配却经办人不匹配；后分配但只监听创建；节点/类型范围不覆盖 |
| 源端执行记录 | 该来源 ID/时间对应的记录和条件结果 | 不满足条件属于跳过；没有记录不能单凭这一点判断 API/MCP 不触发事件 |
| Base 入站记录/日志 | 来源校验、事件 schema、负责人遍历、查重结果 | Token/空间不符、字段引用错、负责人数组为空、已存在映射、旧时间事件被跳过 |
| Base 来源行 | 来源 Key、Linear ID、负责人有效、删除标记、已尝试、同步状态 | 多行映射、停止同步、删除后事件、创建结果不确定 |
| HTTP 节点 | HTTP code、实际请求体、GraphQL data/errors | 整体运行成功仍可能 HTTP 400；200 仍可能 errors 或 success=false |
| Linear | 来源链接/Key、Issue ID、Team、负责人、状态 | 已创建但回写失败；建到其他 Team；实际已同步但本地任务页视图没显示 |
| 可选 Orca 展示 | 相同工作区/Team/账号与过滤范围 | 不把展示筛选误判为同步失败 |

先用已有授权工具查；权限不足时说明未核实的层级，不声称已查全。不要输出凭证。创建/修改一条源业务数据不属于只读诊断。

## 从历史案例复用判断，不复制结论

**案例：本人报告的缺陷没同步。** 实际详情经办人为空；规则明确“创建缺陷时，经办人包含指定人员”；操作历史只有新建。这足以说明当前不符合规则，但不能单凭它断言历史事件一定被过滤。要确认创建时未命中，读取创建快照（经办人为空）或该次执行记录的条件不满足结果；拿不到时明确标注为推断。后补经办人不会触发这条创建规则，需要明确范围的补同步或新增人员变化事件处理。

不要仅凭当前经办人为空推断创建时也为空：先看历史；如果创建时曾匹配、随后移除，必须继续看当时执行记录。用户要求仅解释原因时，不自行给他分配任务或补建 Issue。

**案例：MCP 创建的工作项未同步。** `from mcp` 本身不是根因。先核对工具有没有写入业务经办人/负责人、来源规则是否接收该类型事件和 API 创建范围，再查事件日志。不能规定所有 MCP 创建都不触发、也不能声称所有 API 创建一定触发。

**案例：规则显示成功，Linear 没出现。** 检查节点响应、GraphQL 业务字段以及目标 Team。若已发送但结果不确定，转恢复流程；不要循环“再试一次”。

## 结论形式

用一段话说明阻断层和证据，再给最小修复方向；区分确定事实、推断和未核实项。例：“当前规则按经办人筛选，详情/历史显示未设置经办人；报告人不参与此条件。创建规则不会因后补字段重放。”
